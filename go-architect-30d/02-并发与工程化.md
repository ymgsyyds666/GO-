# 02 · 并发与工程化（D8–D14）

> 这一周决定你"是不是真的会 Go"。并发写不对，服务端就是灾难现场。
> 配套可运行代码：`code/concurrency/`、`code/context/`。

---

## 1. 先把概念摆正

| 概念 | 含义 |
|---|---|
| 并发（concurrency） | 多个任务**交替**推进（逻辑上同时） |
| 并行（parallelism） | 多个任务**物理同时**执行（多核） |
| 协程（goroutine） | Go 运行时调度的用户态线程，初始栈 2KB，可动态增长到 1GB |
| CSP | Communicating Sequential Processes：**通过通信共享内存**，而不是通过共享内存通信 |

```go
// 不要这样共享
var counter int
go func() { counter++ }()  // 数据竞争

// 要这样通信
ch := make(chan int, 1)
go func() { ch <- 1 }()
<-ch
```

goroutine vs 线程：

| 维度 | goroutine | OS 线程 |
|---|---|---|
| 初始栈 | 2KB，按需增长 | 1~8MB 固定 |
| 创建开销 | ~0.2µs | ~10µs+ |
| 切换开销 | ~几十 ns（用户态） | ~1µs（内核态） |
| 数量级 | 百万级 | 万级 |

## 2. GMP 调度模型（面试必考）

```
        ┌─────────────── global runqueue ───────────────┐
        │                                               │
   ┌────┴────┐     ┌─────────┐     ┌─────────┐
   │   P0    │     │   P1    │     │   P2    │   P = 逻辑处理器（GOMAXPROCS 个）
   │ runq256 │     │ runq256 │     │ runq256 │
   └────┬────┘     └────┬────┘     └────┬────┘
        │               │               │
   ┌────┴────┐     ┌────┴────┐     ┌────┴────┐
   │   M0    │     │   M1    │     │   M2    │   M = OS 线程
   └────┬────┘     └────┬────┘     └────┬────┘
        │               │               │
   ┌────┴────┐     ┌────┴────┐     ┌────┴────┐
   │   G     │     │   G     │     │   G     │   G = goroutine
   └─────────┘     └─────────┘     └─────────┘
```

**一条铁律：M 必须持有 P 才能执行 G。**

关键机制：

1. **work stealing**：P 的本地队列空了，先偷全局队列，再随机偷其他 P 的一半 G。
2. **handoff**：G 执行阻塞系统调用时，M 释放 P 交给其他 M，避免 P 空转（网络 IO 走 netpoller，不阻塞 M）。
3. **sysmon**：独立监控线程，每 10ms 检查一次；发现 G 运行超过 10ms 会发信号抢占（Go 1.14+ 异步抢占），并回收卡在系统调用里的 P。
4. **GOMAXPROCS**：默认等于 CPU 核数；Go 1.25 起会自动考虑容器 cgroup 的 CPU 限额。

验证实验：

```go
func main() {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("goroutines=%d\n", runtime.NumGoroutine())
	// 起 10 万个协程，观察内存与耗时
}
```

```bash
GOMAXPROCS=1 go run .   # 单核也能跑并发（只是不并行）
GODEBUG=schedtrace=1000 go run .   # 每秒打印调度器状态
```

> `schedtrace` 输出里重点看 `gomaxprocs`、`runqueue`、`gc` 三列。

## 3. goroutine 与泄漏

```go
go func() {
	defer func() {
		if r := recover(); r != nil {
			log.Printf("goroutine panic: %v", r) // 子协程 panic 会打挂整个进程！
		}
	}()
	doWork()
}()
```

**goroutine 里 panic 不 recover，整个进程退出** —— 后台任务必须自己兜底。

泄漏的四种典型：

```go
// 1. 永久阻塞在发送（无接收者）
go func() { ch <- 1 }()

// 2. 永久阻塞在接收（无人发送）
go func() { <-ch }()

// 3. 忘记 cancel context
ctx, _ := context.WithCancel(context.Background()) // 丢了 cancel

// 4. 循环里起协程但没退出条件
for {
	go consume()   // 无限增长
}
```

检测手段：

```go
// 测试里断言协程数不增长
before := runtime.NumGoroutine()
// ... 被测逻辑
time.Sleep(100 * time.Millisecond)
if after := runtime.NumGoroutine(); after > before {
	t.Fatalf("leak: %d -> %d", before, after)
}
```

生产级用 `go.uber.org/goleak`：

```go
func TestMain(m *testing.M) {
	goleak.VerifyTestMain(m)
}
```

## 4. channel 完全指南（D9）

### 4.1 三种形态

```go
ch := make(chan int)        // 无缓冲：发送阻塞直到有人接收（同步握手）
ch := make(chan int, 10)    // 有缓冲：缓冲满才阻塞
var ch chan int             // nil：读写都永久阻塞（select 里等于禁用该分支）
```

### 4.2 操作语义表（背下来）

| 操作 | nil channel | 已关闭 channel | 正常 channel |
|---|---|---|---|
| 发送 `ch <- v` | 永久阻塞 | **panic** | 阻塞或成功 |
| 接收 `<-ch` | 永久阻塞 | 立即返回零值, `false` | 阻塞或成功 |
| `close(ch)` | panic | panic | 关闭成功 |

```go
ch := make(chan int, 2)
ch <- 1
ch <- 2
close(ch)

for v := range ch {   // 自动在关闭且取空后退出
	fmt.Println(v)    // 1 2
}
v, ok := <-ch
fmt.Println(v, ok)    // 0 false
```

### 4.3 单向 channel（接口约束）

```go
func producer(out chan<- int) { out <- 1 }   // 只能发
func consumer(in <-chan int)  { <-in }       // 只能收

ch := make(chan int)
go producer(ch)
consumer(ch)
```

### 4.4 select：多路复用

```go
select {
case v := <-ch1:
	fmt.Println("ch1", v)
case ch2 <- 1:
	fmt.Println("sent")
case <-time.After(500 * time.Millisecond):
	fmt.Println("timeout")
default:
	fmt.Println("no ready channel")
}
```

要点：

- 多个 case 同时就绪 → **随机选一个**（伪随机，防饥饿）。
- `default` 让 select 非阻塞。
- `nil` channel 的 case 永远不就绪，可用来动态开关分支。
- `time.After` 在 Go 1.23 前会堆积定时器，高频循环里用 `time.NewTicker` 或复用 `Timer`。

超时控制的标准写法：

```go
func doWithTimeout(ctx context.Context, d time.Duration) error {
	ctx, cancel := context.WithTimeout(ctx, d)
	defer cancel()

	done := make(chan error, 1)   // 必须带缓冲，否则超时后协程泄漏
	go func() { done <- work() }()

	select {
	case err := <-done:
		return err
	case <-ctx.Done():
		return ctx.Err()          // context.DeadlineExceeded
	}
}
```

### 4.5 关闭原则

> **谁发送，谁关闭；接收方永远不要关闭 channel。** 多个发送者时，用额外的 `done` channel 或 `sync.Once` 协调。

```go
// 多生产者安全关闭
var wg sync.WaitGroup
done := make(chan struct{})
for i := 0; i < 3; i++ {
	wg.Add(1)
	go func() { defer wg.Done(); produce(done) }()
}
go func() { wg.Wait(); close(done) }()
```

## 5. 并发模式（D12 重点，手写 5 遍）

### 5.1 Worker Pool（最常用）

```go
type Job struct{ ID int }
type Result struct{ ID, Value int }

func workerPool(jobs []Job, workers int) []Result {
	jobCh := make(chan Job, len(jobs))
	resCh := make(chan Result, len(jobs))

	var wg sync.WaitGroup
	for i := 0; i < workers; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := range jobCh {
				resCh <- Result{ID: j.ID, Value: j.ID * 2}
			}
		}()
	}

	for _, j := range jobs { jobCh <- j }
	close(jobCh)

	go func() { wg.Wait(); close(resCh) }()

	var out []Result
	for r := range resCh { out = append(out, r) }
	return out
}
```

> 缓冲大小 = 任务数，避免生产/消费互相等待；真实场景按内存权衡。

### 5.2 Pipeline（流水线）

```go
func gen(nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range nums { out <- n }
	}()
	return out
}

func square(in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for n := range in { out <- n * n }
	}()
	return out
}

// 使用：gen(1,2,3) → square → 消费
for v := range square(gen(1, 2, 3)) { fmt.Println(v) }
```

加取消：每个阶段 `select { case <-ctx.Done(): return }`。

### 5.3 Fan-out / Fan-in

```go
func fanIn(ctx context.Context, chs ...<-chan int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup
	for _, ch := range chs {
		wg.Add(1)
		go func(c <-chan int) {
			defer wg.Done()
			for {
				select {
				case v, ok := <-c:
					if !ok { return }
					select {
					case out <- v:
					case <-ctx.Done():
						return
					}
				case <-ctx.Done():
					return
				}
			}
		}(ch)
	}
	go func() { wg.Wait(); close(out) }()
	return out
}
```

### 5.4 or-channel / 首个完成即返回

```go
func first(ctx context.Context, chs ...<-chan string) string {
	ctx, cancel := context.WithCancel(ctx)
	defer cancel()
	out := make(chan string, len(chs))
	for _, ch := range chs {
		go func(c <-chan string) {
			select {
			case v := <-c:
				select { case out <- v: case <-ctx.Done(): }
			case <-ctx.Done():
			}
		}(ch)
	}
	return <-out
}
```

### 5.5 errgroup：并发任务 + 首个错误取消

```go
import "golang.org/x/sync/errgroup"

func fetchAll(ctx context.Context, urls []string) error {
	g, ctx := errgroup.WithContext(ctx)
	g.SetLimit(10)                     // 并发上限（信号量语义）
	for _, u := range urls {
		g.Go(func() error {
			return fetch(ctx, u)       // 任一出错，ctx 自动取消
		})
	}
	return g.Wait()
}
```

Go 1.22+ 循环变量每次迭代独立，不需要再写 `u := u`。

### 5.6 singleflight：请求合并（缓存击穿神器）

```go
import "golang.org/x/sync/singleflight"

var g singleflight.Group

func GetUser(ctx context.Context, id int64) (*User, error) {
	v, err, _ := g.Do(fmt.Sprint(id), func() (any, error) {
		return loadFromDB(ctx, id)   // 同一 id 的并发请求只打一次 DB
	})
	if err != nil { return nil, err }
	return v.(*User), nil
}
```

### 5.7 令牌桶限流器（手写，面试常考）

```go
type TokenBucket struct {
	mu     sync.Mutex
	rate   float64   // 每秒补充令牌数
	burst  float64   // 桶容量
	tokens float64
	last   time.Time
}

func NewTokenBucket(rate float64, burst int) *TokenBucket {
	return &TokenBucket{rate: rate, burst: float64(burst), tokens: float64(burst), last: time.Now()}
}

func (b *TokenBucket) Allow() bool {
	b.mu.Lock()
	defer b.mu.Unlock()
	now := time.Now()
	b.tokens = min(b.burst, b.tokens+now.Sub(b.last).Seconds()*b.rate)
	b.last = now
	if b.tokens >= 1 {
		b.tokens--
		return true
	}
	return false
}
```

生产直接用：`golang.org/x/time/rate`（`rate.NewLimiter(100, 200)`）。

## 6. sync 包（D10）

### 6.1 Mutex：正常模式与饥饿模式

- 正常模式：自旋 + 排队，允许新来的 goroutine 抢锁（吞吐高，但可能饿死老 goroutine）。
- 等待超过 **1ms**，切换到饥饿模式：锁直接交给队首，新来的不许抢。
- 解锁时若队列为空且无自旋者，直接释放。

```go
var mu sync.Mutex
mu.Lock()
defer mu.Unlock()
```

**不要拷贝含 Mutex 的结构体**（`go vet` 会发现），传参用指针。

### 6.2 RWMutex

读多写少用；但读锁也有开销，**极高并发读场景 sync.Map 或分片锁更优**。

```go
var rw sync.RWMutex
rw.RLock(); defer rw.RUnlock()
rw.Lock();  defer rw.Unlock()
```

### 6.3 WaitGroup

```go
var wg sync.WaitGroup
for i := 0; i < 10; i++ {
	wg.Add(1)
	go func(i int) { defer wg.Done(); work(i) }(i)
}
wg.Wait()
```

Go 1.25 起可直接 `wg.Go(func(){ ... })`，不用手动 Add/Done，且能在 Wait 之后再 Go（更安全）。

### 6.4 Once：单例/惰性初始化

```go
var (
	once sync.Once
	inst *Client
)
func GetClient() *Client {
	once.Do(func() { inst = newClient() })
	return inst
}
```

### 6.5 Pool：对象复用，降低 GC 压力

```go
var bufPool = sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

buf := bufPool.Get().(*bytes.Buffer)
defer func() {
	buf.Reset()
	bufPool.Put(buf)
}()
```

坑：Pool 里的对象**随时可能被 GC 回收**，不能当缓存存有状态的东西。

### 6.6 sync.Map

适合：key 基本不变、读远多于写（如配置缓存、连接池元数据）。不适合：频繁增删。

### 6.7 Cond：等待条件（用得少）

```go
c := sync.NewCond(&sync.Mutex{})
c.L.Lock()
for !ready { c.Wait() }
c.L.Unlock()
c.Broadcast()
```

一般用 channel 更直观。

## 7. atomic 与内存模型（D10）

```go
var counter atomic.Int64
counter.Add(1)
counter.Load()
counter.CompareAndSwap(old, new)

var flag atomic.Bool
flag.Store(true)
```

要点：

- `atomic` 保证单个变量的原子性和**顺序一致性**（Go 1.19 后类型化 API）。
- 复合操作（先读后写）用 CAS 循环或直接加锁。
- 不要用 `int64` + `atomic.AddInt64` 在 32 位平台上操作未对齐字段（用 `atomic.Int64` 类型避免）。
- happens-before：channel 发送先于接收完成；`sync.Once` 的 Do 先于返回；Mutex 解锁先于下次加锁。

## 8. context（D11）

### 8.1 四个构造函数

```go
ctx := context.Background()                    // 根，永不取消
ctx = context.TODO()                           // 不确定时的占位

ctx, cancel := context.WithCancel(parent)      // 手动取消
ctx, cancel := context.WithTimeout(parent, 3*time.Second)
ctx, cancel := context.WithDeadline(parent, time.Now().Add(3*time.Second))
ctx = context.WithValue(parent, key, val)      // 只放请求级元数据
```

### 8.2 规则（官方三条）

1. **不要把 Context 存进结构体**，作为函数第一个参数显式传递，命名为 `ctx`。
2. **不要传 nil**，用 `context.TODO()`。
3. **WithCancel / WithTimeout 必须调用 cancel**（`defer cancel()`），否则泄漏。

### 8.3 超时链

```go
// 入口 5s 总超时，DB 查询 2s，下游 RPC 3s —— 逐层收敛
func (s *Service) Handle(ctx context.Context, req *Req) (*Resp, error) {
	ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
	defer cancel()

	dbCtx, dbCancel := context.WithTimeout(ctx, 2*time.Second)
	defer dbCancel()

	user, err := s.repo.Get(dbCtx, req.ID)
	if err != nil {
		return nil, fmt.Errorf("get user: %w", err)
	}

	rpcCtx, rpcCancel := context.WithTimeout(ctx, 3*time.Second)
	defer rpcCancel()

	return s.rpc.Call(rpcCtx, user)
}
```

### 8.4 用 Value 传递什么？

只放**请求级、不可变**的元数据：traceID、用户 ID、租户 ID。

```go
type ctxKey string
const traceKey ctxKey = "trace_id"

ctx = context.WithValue(ctx, traceKey, "abc123")
v := ctx.Value(traceKey).(string)
```

坑：

- 用自定义类型做 key，避免撞车（不要用 string 字面量）。
- **不要用它传依赖**（DB、配置），那是参数的事。
- 取不到值会返回 nil，断言要 comma-ok。

### 8.5 HTTP 集成

`http.Request.Context()` 在客户端断开时自动取消 —— 把 ctx 一路传下去，下游查询会自动中止，这是防雪崩的关键。

## 10. 性能工程（D13）

### 10.1 逃逸分析

```bash
go build -gcflags='-m -m' ./... 2>&1 | grep -E "escapes|moved to heap"
```

常见逃逸：

- 返回局部变量地址
- 闭包捕获变量
- 接口装箱（`any(x)`、`fmt.Println(x)`）
- 发送指针到 channel
- 切片扩容后旧数组被引用
- map 中存指针

**逃逸不等于性能问题**，但要能解释。

### 10.2 Benchmark

```go
func BenchmarkJoin(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		_ = strings.Join([]string{"a", "b", "c"}, ",")
	}
}
```

```bash
go test -bench=. -benchmem -count=5
go install golang.org/x/perf/cmd/benchstat@latest
benchstat old.txt new.txt   # 比较优化前后，看 p 值和变化幅度
```

### 10.3 pprof

```go
import _ "net/http/pprof"

go func() {
	log.Println(http.ListenAndServe("localhost:6060", nil))

```

```bash
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30   # CPU

```

容器里两个一起用：`GOMEMLIMIT` 设为内存 limit 的 80~90%。

## 12. 反射与 unsafe（知道边界即可）

```go
v := reflect.ValueOf(user)
t := v.Type()
for i := 0; i < t.NumField(); i++ {
	fmt.Println(t.Field(i).Name, v.Field(i).Interface())
}
```

用途：ORM 字段映射、JSON 编解码、配置绑定、参数校验（validator）。

unsafe 三件套：`unsafe.Pointer`、`uintptr`、`Sizeof`。**业务代码禁用**，只在零拷贝、高性能序列化里出现。

## 13. 并发陷阱清单（上线前逐条过）

| # | 陷阱 | 后果 | 方案 |
|---|---|---|---|
| 1 | 子协程 panic 未 recover | 进程退出 | 每个后台协程 defer recover |
| 2 | 循环里 `defer` | 句柄泄漏 | 包函数 |
| 3 | map 并发写 | fatal，不可 recover | 加锁 / sync.Map / 分片 |
| 4 | 无缓冲 channel 配合提前 return | 协程永久阻塞 | 缓冲 + select ctx.Done |
| 5 | 忘记 cancel | context 树泄漏 | `defer cancel()` |
| 6 | 把 ctx 存 struct | 生命周期混乱 | 首参传递 |
| 7 | 用 `time.After` 高频循环 | 定时器堆积（1.23 前） | Ticker / NewTimer |
| 8 | WaitGroup Add 在 goroutine 里 | 竞态，Wait 提前返回 | Add 在外层 |
| 9 | 关闭别人持有的 channel | panic | 谁发送谁关闭 |
| 10 | 拷贝含锁结构体 | 锁失效 | 用指针，vet 检查 |
| 11 | select 无 default 且全忙 | 死锁 | 加超时/ctx |
| 12 | 并发写同一 slice 元素 | 数据竞争 | 预分配 + 下标独立 / 加锁 |

## 14. D14 周项目：GoScan v1（并发化）

**需求**：把 D7 的单协程目录扫描器改造成并发版，支持 worker 数配置、Ctrl+C 优雅退出、协程数监控。

```go
type Scanner struct {
	root    string
	workers int
}

func (s *Scanner) Run(ctx context.Context) (Stats, error) {
	paths := make(chan string, 4096)
	results := make(chan Stats, s.workers)

	go func() {
		defer close(paths)
		filepath.WalkDir(s.root, func(p string, d fs.DirEntry, err error) error {
			if err != nil || d.IsDir() {
				return nil
			}
			select {
			case paths <- p:
			case <-ctx.Done():
				return ctx.Err()
			}
			return nil
		})
	}()

	var wg sync.WaitGroup
	for i := 0; i < s.workers; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			local := Stats{ByExt: map[string]ExtStat{}}
			for p := range paths {
				info, err := os.Stat(p)
				if err != nil {
					continue
				}
				local.add(p, info.Size())
			}
			results <- local
		}()
	}
	go func() { wg.Wait(); close(results) }()

	total := Stats{ByExt: map[string]ExtStat{}}
	for r := range results {
		total.merge(r)
	}
	return total, ctx.Err()
}
```

验收：

- [ ] `go test -race` 通过
- [ ] `SIGINT` 后 2 秒内退出，所有协程回收（goleak 验证）
- [ ] 1 万文件压测，内存平稳，协程数不随时间增长
- [ ] 带 pprof，能说出耗时分布
- [ ] 8 workers 比单协程快 3 倍以上
