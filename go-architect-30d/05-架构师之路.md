# 05 · 架构师之路（D22、D28）

> 架构师 ≠ 写代码最多的人。架构师 = **在资源、时间、团队的约束下，做出可解释的取舍，并保证方案能落地**。
> 这一章给你"思考框架 + 工具箱"，配合前四章的技术，才能在面试和工作中讲出深度。

---

## 1. 架构师每天在做什么

| 职责 | 具体动作 | 产出 |
|---|---|---|
| 需求翻译 | 把业务语言翻译成质量属性（QPS、延迟、一致性、可用性） | 非功能性需求清单 |
| 方案设计 | 画架构图、定边界、选技术、算容量 | 设计文档 + ADR |
| 风险识别 | 单点、瓶颈、依赖、安全、成本 | 风险清单 + 预案 |
| 落地推进 | 拆任务、定接口、Code Review、联调 | 里程碑 |
| 演进治理 | 监控、复盘、还技术债 | 迭代计划 |

**和高级开发的区别**：开发对"功能正确"负责，架构师对"**三个月后还能不能改、扛不扛得住、出问题能不能兜住**"负责。

## 2. 从需求到架构：五步法

### 第一步：问清约束（比画图重要 10 倍）

必问清单：

- 用户量 / DAU / 峰值 QPS 是多少？增长预期？
- 延迟要求（P99 多少 ms）？可用性要求（几个 9）？
- 数据一致性要求（强一致 / 最终一致）？能丢数据吗？
- 预算（机器、云服务）、团队规模与技术栈、上线时间？
- 合规要求（等保、数据出境、审计）？

### 第二步：定义质量属性（可度量）

```
可用性：99.95%（月停机 ≤ 21.6 分钟）
性能：P99 < 200ms，峰值 5000 QPS
一致性：订单强一致，统计报表 T+1 最终一致
可扩展：单表 5000 万行前可平滑分片
成本：单请求成本 < 0.002 元
```

### 第三步：划分边界

- 按**业务能力**划分（用户、订单、支付、库存），不是按技术分层。
- 明确每个模块的**数据所有权**：一个数据只有一个写入口。
- 定义**同步/异步**边界：核心链路同步，非核心异步。

### 第四步：做取舍（写下来）

每个决策都写 ADR（见第 9 节），至少包含：选了什么、放弃了什么、什么条件下推翻。

### 第五步：验证

- 压测、故障演练、容量验证。
- 用"如果流量涨 10 倍 / 依赖挂一个"反问自己的设计。

## 3. 容量评估（面试必考，工作中必用）

### 3.1 基本公式

```
平均 QPS = 日请求量 / 86400
峰值 QPS = 平均 QPS × 峰值系数（一般 3~5，活动场景 10+）
实例数   = 峰值 QPS / 单实例 QPS × (1 + 冗余系数 0.3~0.5)
DB 连接数 = 实例数 × maxOpenConns（注意 DB 总连接上限）
存储     = 日增数据 × 保留天数 × 副本数 × 索引放大系数(1.3~2)
带宽     = 峰值 QPS × 平均响应大小 × 8（bit）
```

### 3.2 完整算例：短链服务

假设：

- DAU 100 万，人均每天生成 2 条、访问 20 次
- 读:写 = 10:1
- 单条记录 500B，保留 3 年

```
写 QPS  = 100w × 2 / 86400 ≈ 23，峰值 ×4 ≈ 100
读 QPS  = 100w × 20 / 86400 ≈ 231，峰值 ×4 ≈ 1000
总 QPS  ≈ 1100

单实例（Gin + Redis 命中 95%）可扛 3000 QPS
实例数 = 1100 / 3000 ≈ 0.4 → 至少 2 台（高可用）

连接数 = 2 × 50 = 100 < MySQL 默认 151 ✅

存储 = 200w 条/天 × 500B ≈ 1GB/天
     × 365 × 3 年 ≈ 1TB，× 副本 2 ≈ 2TB
     → 单机 MySQL 可撑，无需分库；按 code 哈希分表可选

带宽 = 1100 × 1KB × 8 ≈ 8.8 Mbps（很小）
```

结论：**瓶颈在 DB 写入和短链查询，不在带宽**。所以设计重点：Redis 缓存 + 发号器 + 异步统计。

### 3.3 常用经验值（背下来，面试直接用）

| 组件 | 单实例能力（量级） |
|---|---|
| Nginx | 5w~10w QPS（静态） |
| Go 简单 HTTP 服务 | 2w~5w QPS（本地回环） |
| Gin + JSON + Redis | 3k~1w QPS |
| MySQL（单机，SSD，简单查询） | 2k~8k QPS |
| Redis（单实例） | 5w~10w QPS |
| Kafka（单分区） | 写入 10w+/s |
| 单机 TCP 长连接 | 1w~5w（调优后 10w+） |

> 这些数字只用于**量级估算**，真实值必须压测。面试时说"量级"即可。

## 4. 分层架构与 DDD-lite（Go 落地版）

### 4.1 不要照搬 DDD 全套

Go 社区实践：**DDD-lite** —— 借概念，不搞仪式。

```
cmd/                 入口，装配
internal/
├── handler/         HTTP/gRPC 适配层：参数校验、DTO 转换、调用 service
├── service/         应用层：用例编排、事务边界、权限校验
├── domain/          领域层：实体、值对象、领域服务、仓储接口
├── repository/      基础设施：MySQL/Redis 实现，实现 domain 的接口
└── pkg/             通用工具
```

依赖方向：`handler → service → domain ← repository`。**domain 不依赖任何框架**，这是可测试性的关键。

### 4.2 用接口做依赖倒置

```go
// domain/user.go —— 只定义接口，不知道 MySQL 的存在
type UserRepository interface {
	Get(ctx context.Context, id int64) (*User, error)
	Save(ctx context.Context, u *User) error
}
```

```go
// repository/mysql/user.go
type userRepo struct{ db *sqlx.DB }
func (r *userRepo) Get(ctx context.Context, id int64) (*domain.User, error) { ... }
```

好处：service 可以用 fake repo 做单测，不依赖数据库。

### 4.3 什么时候该拆服务？

| 信号 | 说明 |
|---|---|
| 团队规模 > 10 人，代码冲突频繁 | 按团队边界拆 |
| 某模块需要独立扩容 | 拆出高负载服务 |
| 某模块发布频率差异大 | 独立发布 |
| 技术栈不同（AI 用 Python） | 按语言拆 |
| 单体编译 > 5 分钟 | 拆模块（不一定拆服务） |

**反例**：3 个人、日活 1000，就上 8 个微服务 —— 运维成本会压垮团队。

> 架构演进路径：**单体（模块清晰）→ 模块化单体 → 按需拆 2~3 个服务 → 微服务**。

## 5. 高并发的五个杠杆

按性价比排序：

| 杠杆 | 手段 | 效果 |
|---|---|---|
| 1. 缓存 | 本地 + Redis，命中率 95%+ | 减少 90% DB 压力 |
| 2. 异步 | MQ 削峰，非核心链路异步化 | 峰值削平 |
| 3. 读写分离/分片 | 主从、按 key 哈希 | 水平扩展存储 |
| 4. 无状态 | 会话外置（Redis/JWT） | 任意扩容 |
| 5. 限流降级 | 保护核心链路 | 防止雪崩 |

### 5.1 秒杀系统的分层过滤

```
CDN/静态化 → 网关限流 → 前端按钮防重 → Redis 预扣库存
→ MQ 异步下单 → DB 落库 → 订单状态轮询
```

关键点：

- **库存预扣用 Lua 保证原子**：`if stock > 0 then decr; return 1 else return 0`。
- 只有预扣成功的请求才进 MQ，DB 压力从 10w 降到 1k。
- 超卖兜底：DB `UPDATE stock SET n = n - 1 WHERE id = ? AND n > 0`。
- 幂等：用户 ID + 商品 ID 唯一索引。

### 5.2 热点 key 治理

- 本地缓存（1s TTL）挡住 99% 流量。
- key 加随机后缀打散到多个 Redis 实例（读时聚合）。
- 大 key 拆分（Hash 分桶）。
- 监控：`redis-cli --hotkeys`、慢日志。

## 6. 数据一致性方案

| 场景 | 方案 | 一致性 |
|---|---|---|
| 单库多表 | 本地事务 | 强一致 |
| 订单 + 库存（同库） | 本地事务 | 强一致 |
| 跨服务（可容忍延迟） | **本地消息表 / Outbox** | 最终一致 |
| 跨服务（需补偿） | Saga | 最终一致 |
| 资金类（强一致） | TCC / 2PC（少用） | 较强 |
| 缓存与 DB | 先更新 DB 再删缓存 + 延迟双删 | 最终一致 |

### Outbox 模式（最推荐落地）

```
业务事务里同时写：订单表 + outbox 表（同一个 DB 事务）
  → 独立投递器轮询 outbox → 发 MQ → 标记已发送
  → 消费方幂等处理
```

优点：不依赖 MQ 事务消息，实现简单，可靠。

```sql
CREATE TABLE outbox (
  id bigserial PRIMARY KEY,
  topic varchar(100),
  payload jsonb,
  status smallint DEFAULT 0,  -- 0 待发 1 已发
  created_at timestamptz DEFAULT now()
);
```

### 幂等的三种实现

1. **唯一索引**：`INSERT ... ON CONFLICT DO NOTHING`（最可靠）。
2. **状态机**：`UPDATE ... WHERE status = 'pending'`，影响行数为 0 则跳过。
3. **去重表/Redis SETNX**：记录已处理的消息 ID（注意 TTL 与持久化）。

## 7. 稳定性工程

### 7.1 SLO 与错误预算

| SLO | 月停机 | 含义 |
|---|---|---|
| 99% | 7.2 小时 | 内部系统 |
| 99.9% | 43.2 分钟 | 一般业务 |
| 99.95% | 21.6 分钟 | 核心业务 |
| 99.99% | 4.32 分钟 | 支付级 |

**错误预算**：99.9% → 每月可"失败" 43 分钟。预算用完就停止发版、专注稳定性。

### 7.2 稳定性四板斧

1. **冗余**：多实例、多可用区、多供应商（LLM/OCR 至少两家）。
2. **隔离**：线程池/连接池隔离，核心与非核心分离，避免级联。
3. **限制**：超时、限流、熔断、队列长度上限（**没有上限的队列就是内存泄漏**）。
4. **可观测**：黄金指标（延迟、流量、错误、饱和度）+ 告警 + 值班。

### 7.3 熔断器状态机

```
Closed（正常） --连续失败达阈值--> Open（直接拒绝）
Open --等待窗口--> Half-Open（放少量请求试探）
Half-Open --成功--> Closed
Half-Open --失败--> Open
```

```go
import "github.com/sony/gobreaker"

cb := gobreaker.NewCircuitBreaker(gobreaker.Settings{
	Name:        "ocr",
	MaxRequests: 5,
	Interval:    30 * time.Second,
	Timeout:     10 * time.Second,
	ReadyToTrip: func(c gobreaker.Counts) bool {
		return c.ConsecutiveFailures > 5
	},
})

result, err := cb.Execute(func() (any, error) {
	return ocrClient.Recognize(ctx, file)
})
```

### 7.4 故障演练（Chaos）

在预发做，别在生产做：

- 杀掉一个实例 → 验证 LB 摘流和客户端重试。
- 停 Redis → 验证降级到 DB（可能慢，但不能挂）。
- DB 主从切换 → 验证连接池自动重连。
- 注入 500ms 延迟 → 验证超时链路。
- MQ 堆积 → 验证消费扩容与磁盘告警。

### 7.5 故障复盘模板（不追责，追机制）

```markdown
## 故障标题：2026-xx-xx 短链跳转 5xx 上升
- 影响：xx 分钟，xx% 请求失败
- 时间线：T0 告警 → T1 定位 → T2 止血 → T3 恢复
- 根因：Redis 连接池耗尽（慢查询阻塞）
- 为什么没早发现：没有 Redis 慢查询告警
- 改进项（有 owner 有 deadline）：
  1. 增加慢查询监控（@张三，xx-xx）
  2. 连接池隔离 + 超时 200ms（@李四，xx-xx）
```

## 8. 可演进性设计

- **API 版本化**：只增字段不删（向后兼容），破坏性变更走 `/v2`。
- **灰度**：按用户/流量比例/地域分流；开关用配置中心，可秒级回滚。
- **数据兼容**：schema 变更遵循"扩展-迁移-收缩"，先加新列双写，再切读，最后删旧列。
- **抽象边界**：第三方依赖（OCR/LLM/短信）都包一层接口，方便替换与降级。

```go
type OCREngine interface {
	Recognize(ctx context.Context, img []byte) ([]Line, error)
}

// 实现：cloud / paddle / tesseract / mock —— 可插拔
```

## 9. 技术选型方法论 + ADR

### 9.1 选型打分表

| 维度 | 权重 | 说明 |
|---|---|---|
| 满足需求 | 30% | 功能、性能、精度 |
| 团队熟悉度 | 20% | 学习成本、招聘难度 |
| 生态与社区 | 15% | 文档、issue 响应、长期维护 |
| 运维成本 | 15% | 组件数量、监控、升级 |
| 成本 | 10% | 机器、云服务、人力 |
| 风险 | 10% | 锁定、License、停止维护 |

用表格给候选方案打分，**结论才站得住**。

### 9.2 ADR 模板（Architecture Decision Record）

```markdown
# ADR-003：短链发号方案

状态：已采纳（2026-11-20）
背景：需要生成全局唯一、不可猜测、长度短的 code，写 QPS ~100。
候选：
  A. UUID 截断 —— 有碰撞风险，长度长
  B. MySQL 自增 ID + Base62 —— 简单，但依赖 DB，重启无影响
  C. Redis INCR + Base62 —— 快，但 Redis 丢数据会跳号（可接受）
  D. 雪花算法 —— 无需中心，但长度 19 位，转 62 进制后 11 位，偏长

决策：选 C（Redis INCR 号段，一次取 1000 个缓存本地）。
理由：写 QPS 低、跳号可接受、实现简单、性能好。
放弃：绝对连续（B）与无中心（D）。
重新评估条件：写 QPS > 5w，或 Redis 不可用时要求继续发号。
```

> ADR 是面试加分项：它证明你"想过"，而不只是"用了"。

## 10. Go 专项 Code Review 清单

**正确性**

- [ ] 错误都被处理，没有 `_ =` 忽略（除非有注释说明）
- [ ] `context` 一路传递，超时设置合理
- [ ] goroutine 都有退出路径，无泄漏
- [ ] `defer` 不在大循环里
- [ ] map 无并发写；共享变量有锁或 channel
- [ ] 切片/数组边界、空指针、类型断言都做了防护
- [ ] 事务边界正确（不跨 RPC）
- [ ] 幂等：重试/重复消费不会产生脏数据

**性能**

- [ ] 循环内无重复 DB/RPC 调用（N+1）
- [ ] 大对象预分配；字符串拼接用 Builder
- [ ] 连接池参数已设置
- [ ] 分页有上限（防 `LIMIT 1000000`）
- [ ] 日志不打大对象、不拼 SQL

**可维护**

- [ ] 函数 < 50 行，嵌套 < 4 层
- [ ] 命名自解释，无 `data`、`info`、`tmp`
- [ ] 接口窄，依赖倒置
- [ ] 有单测，覆盖核心分支和错误路径
- [ ] 魔法数字变常量

**安全**

- [ ] SQL 参数化
- [ ] 输入校验（长度、类型、范围）
- [ ] 日志脱敏
- [ ] 权限校验在服务端（不信任前端）
- [ ] 密钥不入库、不入日志、不入 Git

**上线**

- [ ] 有监控指标和告警
- [ ] 有降级开关
- [ ] 兼容旧版本（灰度期间新旧实例共存）
- [ ] 数据迁移可回滚

## 12. 高频系统设计题思路

### 12.1 短链

`发号（Redis INCR/号段）→ Base62 → 存 DB → 缓存 → 302 跳转 → 异步统计`
加分项：自定义短码、过期清理、防刷、统计去重（HyperLogLog）。

### 12.2 秒杀

`静态化 → 网关限流 → Redis Lua 预扣 → MQ → 异步下单 → 状态轮询`
加分项：库存分桶、答题/验证码、公平性（按请求时间）、超卖兜底。

### 12.3 IM

`长连接网关（WebSocket）→ 消息服务 → 存储（写扩散/读扩散）→ 推送`
关键：连接保活、消息可靠（ACK + 重发）、离线消息、多端同步、顺序性。

### 12.4 Feed 流

`推模式（写扩散，大 V 除外）/ 拉模式（读扩散）/ 推拉结合`
关键：收件箱表、分页游标、去重、热度排序。

### 12.5 支付

`下单 → 支付网关 → 渠道回调 → 状态机 → 对账`
关键：幂等、状态机、回调验签、对账补偿、资金安全。

## 13. 从开发到架构师的成长路径

| 阶段 | 重点 | 标志 |
|---|---|---|
| 初级（0~2 年） | 把功能写对、写好测试 | 代码可维护 |
| 中级（2~4 年） | 性能、并发、排障 | 能独立负责一个服务 |
| 高级（4~6 年） | 系统设计、跨团队协作 | 能主导一个系统的演进 |
| 架构师 | 取舍、治理、技术规划 | 方案被采纳并落地 |

**刻意练习**：

1. 每做一个需求，多问一句"如果流量 ×10 会怎样"。
2. 每次故障，写复盘而不是只修 bug。
3. 每月读一个开源项目的核心模块，画调用图。
4. 每季度做一次技术分享（讲清楚 = 真懂）。
5. 维护一份自己的"决策日志"，半年后回看哪些判断错了。
