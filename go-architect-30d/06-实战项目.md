## 项目一：GoScan（D7 + D14）

**定位**：把第一、二周的知识串起来。CLI 工具，无外部依赖，**重点练并发与工程规范**。

### 1.1 需求

```
goscan scan ./path --workers 8 --top 10
```

- 递归遍历目录，统计：文件数、总大小、按扩展名分组、Top N 大文件
- 跳过符号链接循环、跳过无权限目录（不中断）
- 输出人类可读的大小（KB/MB/GB）
- 支持 `--json` 输出，方便管道处理
- 支持 `Ctrl+C` 优雅退出，打印已扫描部分

### 1.2 v0（D7）：单协程基线

只用 `filepath.WalkDir` + `map`，先跑通，记录耗时。

```go
func walk(root string) (Stats, error) {
	s := Stats{ByExt: map[string]ExtStat{}}
	err := filepath.WalkDir(root, func(path string, d fs.DirEntry, err error) error {
		if err != nil {
			return nil // 跳过无权限，不中断
		}
		if d.IsDir() {
			return nil
		}
		info, err := d.Info()
		if err != nil {
			return nil
		}
		ext := strings.ToLower(filepath.Ext(path))
		es := s.ByExt[ext]
		es.Count++
		es.Size += info.Size()
		s.ByExt[ext] = es
		s.TotalFiles++
		s.TotalSize += info.Size()
		return nil
	})
	return s, err
}
```

### 1.3 v1（D14）：并发化

改造点：

1. **生产者-消费者**：目录遍历是生产者，`file.Info()` 与统计是消费者。
2. **worker pool**：`--workers` 控制并发。
3. **context 取消**：`signal.NotifyContext` 捕获 Ctrl+C。
4. **结果聚合**：每个 worker 汇总局部 map，最后合并（减少锁竞争）。
5. **进度输出**：每 1000 个文件打印一次（用 atomic 计数）。

```go
type ExtStat struct {
	Count int
	Size  int64
}

type Stats struct {
	TotalFiles int
	TotalSize  int64
	ByExt      map[string]ExtStat
}

func (s *Stats) add(path string, size int64) {
	ext := strings.ToLower(filepath.Ext(path))
	es := s.ByExt[ext]
	es.Count++
	es.Size += size
	s.ByExt[ext] = es
	s.TotalFiles++
	s.TotalSize += size
}

func (s *Stats) merge(o Stats) {
	for k, v := range o.ByExt {
		es := s.ByExt[k]
		es.Count += v.Count
		es.Size += v.Size
		s.ByExt[k] = es
	}
	s.TotalFiles += o.TotalFiles
	s.TotalSize += o.TotalSize
}

type Scanner struct {
	root    string
	workers int
}

func (s *Scanner) Run(ctx context.Context) (Stats, error) {
	paths := make(chan string, 4096)
	results := make(chan Stats, s.workers)

	// 生产者
	go func() {
		defer close(paths)
		filepath.WalkDir(s.root, func(p string, d fs.DirEntry, err error) error {
			if err != nil || d.IsDir() {
				return nil
			}
			select {
			case paths <- p:
			case <-ctx.Done():
				return ctx.Err()
			}
			return nil
		})
	}()

	// 消费者
	var wg sync.WaitGroup
	for i := 0; i < s.workers; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			local := Stats{ByExt: map[string]ExtStat{}}
			for p := range paths {
				info, err := os.Stat(p)
				if err != nil {
					continue
				}
				local.add(p, info.Size())
			}
			results <- local
		}()
	}
	go func() { wg.Wait(); close(results) }()

	// 合并
	total := Stats{ByExt: map[string]ExtStat{}}
	for r := range results {
		total.merge(r)
	}
	return total, ctx.Err()
}
```

### 1.4 验收

- [ ] 1 万个文件、8 workers，比 v0 快 3 倍以上
- [ ] `-race` 无告警
- [ ] Ctrl+C 后 1 秒内退出，无 goroutine 泄漏（goleak）
- [ ] `--json` 输出可被 `jq` 解析
- [ ] 5 个单元测试（含边界：空目录、无权限、符号链接）

### 1.5 面试怎么讲

> "我用 Go 写了一个并发目录扫描器。第一版用 WalkDir 单协程，10 万文件要 8 秒；分析后发现瓶颈在 syscall。改成生产者-消费者 + 8 个 worker，每个 worker 聚合局部统计再合并，降到 1.8 秒。中途遇到 WalkDir 回调里直接写 map 的竞态，用 -race 定位后改为局部 map 聚合。还加了 signal.NotifyContext 做优雅退出。"

**考点覆盖**：goroutine、channel、select、context、sync.WaitGroup、atomic、性能对比、race detector。

### 2.4 关键实现

**发号（Redis 号段模式）**

```go
type IDAllocator struct {
	rdb    *redis.Client
	mu     sync.Mutex
	cur    int64
	max    int64
	step   int64
}

func (a *IDAllocator) Next(ctx context.Context) (int64, error) {
	a.mu.Lock()
	defer a.mu.Unlock()
	if a.cur >= a.max {
		max, err := a.rdb.IncrBy(ctx, "shortlink:seq", a.step).Result()
		if err != nil {
			return 0, err
		}
		a.cur = max - a.step
		a.max = max
	}
	a.cur++
	return a.cur, nil
}

// Base62
const alphabet = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

func Encode(n int64) string {
	if n == 0 {
		return "0"
	}
	var b [11]byte
	i := len(b)
	for n > 0 {
		i--
		b[i] = alphabet[n%62]
		n /= 62
	}
	return string(b[i:])
}
```

```go
func (s *Service) Resolve(ctx context.Context, code string) (string, error) {
	key := "link:" + code
	url, err := s.rdb.Get(ctx, key).Result()
	if err == nil {
		if url == "" {
			return "", ErrNotFound          // 空值缓存
		}
		s.incrAsync(code)
		return url, nil
	}
	if !errors.Is(err, redis.Nil) {
		return "", err
	}

	link, err := s.repo.GetByCode(ctx, code)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			s.rdb.Set(ctx, key, "", time.Minute)
			return "", ErrNotFound
		}
		return "", err
	}
	if link.ExpireAt.Valid && link.ExpireAt.Time.Before(time.Now()) {
		return "", ErrExpired
	}

	ttl := 24 * time.Hour
	s.rdb.Set(ctx, key, link.URL, ttl)
	s.incrAsync(code)
	return link.URL, nil
}
```

## 项目三：DocFlow 文档智能处理平台（D24–D27）

**定位**：体现"AI + 工程"的差异化，直接对应公司的 OCR/AI 场景。**面试最亮眼的项目。**

### 3.1 需求

用户上传发票/合同图片或 PDF，系统：

1. 异步 OCR 识别
2. LLM 抽取结构化字段（发票号、金额、日期、抬头）
3. 低置信度转人工复核
4. 结果导出 JSON/Excel
5. 支持批量上传与进度查询

### 3.2 架构

```
┌─────────┐    ┌──────────┐    ┌───────────┐    ┌────────────┐
│ Web/API │───▶│ 对象存储  │───▶│ Kafka     │───▶│ OCR Worker │
└─────────┘    └──────────┘    └───────────┘    └─────┬──────┘
      │                                               │
      │  轮询任务状态                                   ▼
      │                                        ┌─────────────┐
      └───────────────────────────────────────▶│ LLM 结构化   │
                                               └──────┬──────┘
                                                      ▼
                                               ┌─────────────┐
                                               │ MySQL + Redis│
                                               └─────────────┘
```

### 3.3 里程碑

| 天 | 任务 | 验收 |
|---|---|---|
| D24 | 跑通 PaddleOCR（Docker）+ 云 OCR 对比 | 两种方案各识别 10 张，记录准确率/耗时/成本 |
| D25 | LLM 抽取 + 流式接口 | 输入 OCR 文本，输出 JSON，字段准确率 > 90% |
| D26 | 异步任务 + 状态机 + 重试 + 幂等 | 重复上传只处理一次；OCR 挂了能补 |
| D27 | 人工复核页 + 导出 + 压测 | 端到端 P99 < 5s，20 张/秒 |

### 3.4 关键设计

**任务状态机**

```
pending → processing → success
                    ↘ failed → (retry) → failed_permanent → review
                    ↘ review（低置信度）
```

**降级链**

```
PaddleOCR 超时 → 云 OCR 兜底 → 都失败 → 标记人工
LLM 抽取失败 → 正则规则抽取 → 仍失败 → 返回空字段 + 待复核
```

**成本控制**

- 同一文件 SHA256 去重，不重复调 OCR/LLM。
- 简单模板（固定版式）走正则，不调 LLM。
- LLM 用便宜模型做抽取，复杂字段才升级。

### 3.5 验收

- [ ] 100 张发票测试集，字段准确率 > 95%
- [ ] OCR 服务宕机，任务不丢、恢复后自动补偿
- [ ] 同一文件上传 3 次，任务只创建 1 个
- [ ] 有 Prometheus 指标：任务数、成功率、OCR 耗时、token 消耗
- [ ] 有成本报表：平均每张成本

### 3.6 面试怎么讲

> "DocFlow 是一个发票识别平台。核心矛盾是准确率和成本：纯云 OCR 太贵，纯自建精度不够。我用分层策略——PaddleOCR 处理 90% 的标准发票，置信度低的 10% 走视觉大模型兜底，再不行转人工。工程上用 Kafka 解耦上传和识别，任务状态机 + 幂等表保证不重不漏。压测下来单机 20 张/秒，平均成本 3 分钱一张。"

**考点覆盖**：异步架构、幂等、降级、成本、OCR/LLM 工程化。
